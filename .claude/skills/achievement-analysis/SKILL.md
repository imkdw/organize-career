# Achievement Analysis - 성과 추출 방법론

## 분석 흐름

1. `_workspace/normalized/summary.md`를 읽고 전체 지형(프로젝트, 에픽, 기간)을 파악한다.
2. 담당 클러스터의 이슈를 필터링한다 (조회 패턴은 `career-data-prep` 스킬 참조).
3. 이슈 제목/설명에서 기술적 주제를 식별하고, 관련 PR/Confluence 문서를 Jira 키로 연결한다.
4. 주제별로 성과 단위를 작성한다.

## 성과 단위 포맷

산출물 파일의 각 성과는 이 구조를 따른다:

```markdown
### {성과 제목 - 동사로 끝나는 한 줄}

- **기간**: YYYY-MM ~ YYYY-MM
- **배경**: 왜 이 작업이 필요했는가 (1~2문장)
- **작업 내용**: 무엇을 어떻게 했는가 (기술적 접근 중심, 3~5개 불릿)
- **의사결정**: 검토한 대안과 선택 이유 (트레이드오프가 데이터에 남아있는 경우만 - 주로 Confluence 설계문서. 없으면 "기록 없음")
- **규모/결과**: 셀 수 있는 것 전부 (이슈 N건, PR N건, 관련 도메인 등)
- **기술 스택**: 데이터에서 확인된 것만
- **근거**: PPLSC-123, PPLSC-456, PR#4776, confluence:390397955
- **임팩트 등급**: A(비즈니스/사용자 효과가 문서로 확인) / B(설계 판단이 드러남) / C(엔지니어링 지표) / D(규모뿐)
```

## 클러스터링 규칙

- **1차 시드는 에픽.** summary.md의 에픽 목록에서 하위 이슈 수가 많은 순으로 본다. 에픽 = 프로젝트 단위 성과일 확률이 높다.
- **에픽 없는 이슈(고아 이슈)가 절반 이상이다.** 제목의 대괄호 태그([BE], [FE] 등)와 반복 키워드(결제, 예약, 재고, 권한 등)로 주제 묶음을 만든다.
- 하위 이슈 3건 미만 에픽은 인접 주제에 흡수시킨다.

## 정량화 규칙

- 숫자는 반드시 데이터에서 직접 센다. grep -c 또는 node 집계를 쓰고, 산출 명령을 성과 단위에 주석으로 남기지는 않되 근거 ID로 재현 가능하게 한다.
- **비즈니스 효과(매출, 시간 절감 등)는 데이터에 없다.** 만들어내지 않는다. Confluence 문서에 명시된 경우만 인용하고 문서 ID를 근거로 단다.
- 기간은 클러스터 내 이슈의 created 최소 ~ resolved 최대로 계산한다.

## 데이터 소스별 특성 (실측 기반)

- **Jira desc는 대부분 비어있고, PR body는 템플릿 보일러플레이트다.** 기술적 깊이(설계 판단, 트레이드오프)는 Confluence 본문에서 나온다. 클러스터 이슈 필터링 후 반드시 관련 Confluence 문서를 키워드로 찾아 읽어라.
- **가장 강한 서사는 "설계 문서 → 구현 → 리팩터링" 궤적이다.** 착수 전 작성한 설계/제안 문서와 이후 refactor 라벨 PR이 연결되면 설계 역량의 최상급 근거가 된다. 이 패턴을 우선 탐색하라.
- 이슈-PR 대응률이 높으므로(약 98%) PR이 안 붙은 이슈는 문서 작업이거나 타인 구현일 가능성을 의심하라.

## 하지 말 것

- 이슈 목록 나열을 분석이라고 부르지 않는다. 성과 단위 1개 = 여러 이슈를 관통하는 하나의 기술 이야기.
- "다양한", "수많은" 같은 비정량 수식어로 규모를 표현하지 않는다.
- 데이터에 없는 기술 스택 추정 금지. PR 제목/본문, 이슈 설명, Confluence 본문에서 확인된 것만.

## 산출물

```markdown
(위 포맷 반복, 임팩트 큰 순)

## 다른 클러스터 참고사항
(경계 밖 발견, 없으면 "없음")
```
